# 《轮回online》Unity 手机原生原型实施方案

状态：原型设计，尚未创建 Unity 工程；本文中的模块、协议与性能数值均为拟议方案。
玩法与命名以 [PROTOTYPE_DESIGN.md](PROTOTYPE_DESIGN.md) 为准；本文补充实现边界与技术验收。
目标：以用户提供的原版规则为主要玩法参考，制作画面精美、可原生安装的手机 3D MMO，先验证三职业、探索、宝宝与四人试炼。
制作采用双轨：灰盒持续验证手感与规则，同时完成一段代表最终方向的精美场景；低多边形占位不代表最终画质。
平台：Android APK 原型优先；iOS 同为目标平台，需要 Mac、Xcode、签名及真实 iPhone 验收。PC 仅用于编辑器开发和调试。

## 1. 技术选型

| 部分 | 建议 | 使用边界 |
| --- | --- | --- |
| 引擎 | Unity 6 系列中实施时仍受支持的 LTS + URP | 建工程时核对支持状态，锁定具体编辑器补丁版本与包版本 |
| 输入 | Input System + 多点触控 | 横屏左摇杆、右侧动作区、空白区域拖动镜头；键鼠只作编辑器映射 |
| 镜头 | Cinemachine | 第三人称跟随、避障、软锁定、触控旋转；镜头抖动可关闭 |
| 角色 | CharacterController + Animator | 灰盒阶段代码驱动位移；动画跟随权威动作状态 |
| 寻路 | AI Navigation | 客户端展示与灰盒 AI；Java 服务器需要独立导航实现 |
| 界面 | UGUI + TextMeshPro | HUD、队伍、背包、交互、加载和重连；按输入焦点切换控制 |
| 资源 | Addressables | 按首区、职业、宝宝及后续世界分组；下载层另行实现并验证取消、恢复与内容完整性校验 |
| 建模 | Blender -> FBX | FBX 走 Unity 模型导入流程，统一比例、骨骼、材质和动画命名 |
| 补充格式 | glTF / GLB | 需要验证并锁定兼容的导入包，例如 glTFast；不能视为 FBX 的无配置替代 |
| 网络 | HTTPS + ioGame External 的 WSS | 账户与低频操作走 HTTP；实时输入、状态和事件走连接协议 |
| 原生构建 | Android ARM64/IL2CPP，iOS IL2CPP/Metal | Android 用安装 APK 验证；iOS 在 Mac/Xcode 构建签名后验收，不用模拟器代替 |

版本清单提交 `ProjectVersion.txt`、`Packages/manifest.json` 和 `Packages/packages-lock.json`；使用文本序列化并提交 `.meta`。
Android 商店发行时再准备 AAB 与渠道签名，iOS 分发按测试渠道及签名要求配置；本阶段只设计，不生成或发布安装包。
大型二进制资源使用 Git LFS；先核对存储配额，再确定是否纳入源模型和高分辨率贴图。
不在第一阶段引入 DOTS/ECS、多套网络框架或自研渲染管线；增加依赖必须对应已发现的瓶颈。

## 2. 未来工程结构

```text
unity-client/
  Assets/_Game/
    Scenes/         Boot, Login, Town, AdventureField, WenbaoTrial, ZhenbaoArena
    Runtime/
      Bootstrap/    启动、配置、场景生命周期
      Platform/     前后台、网络切换、安全区、触控与设备质量档
      Player/       输入、角色运动、动画、镜头
      World/        场景实体、交互、导航表现
      Combat/       技能表现、预警、反馈、战斗状态展示
      Pets/         跟随、指令、技能表现
      Networking/   外部帧、契约、连接、快照与预测
      UI/           HUD、菜单、队伍、加载与异常状态
      Data/         静态配置定义与运行时状态模型
    Content/        Prefabs、Materials、Audio、VFX、配置资产
    Editor/         配置校验、构建与内容导出
    Tests/          契约样本、关键状态流与联网验证
  Packages/
  ProjectSettings/
```

运行时代码按实际依赖划分少量程序集；网络 DTO 不引用场景对象，UI 不直接修改权威角色数据。
`Boot` 常驻连接、音频和加载协调器，使用显式生命周期，避免多个场景重复创建全局对象。

## 3. 场景与加载

| 场景 | 原型职责 | 出入口与失败处理 |
| --- | --- | --- |
| Boot | 配置校验、资源目录、服务初始化 | 失败显示重试；禁止带缺失配置进入游戏 |
| Login | 登录、选角或固定测试角色 | 登录成功后申请入场；认证过期回到登录 |
| Town | 小镇，接任务、宝宝整备、组队、盟会与材料市场 | 通过出口去探险片区；按条件进入宝山活动 |
| AdventureField | 一片探险区域，基础遭遇、探索和共享活动 | 服务端确认入区后恢复控制 |
| WenbaoTrial | 文宝山四人迷宫试炼，合作机关、山门守卫与个人奖励 | 全员准备后入场，结束返镇；失败与重连由服务器处理 |
| ZhenbaoArena | P3 珍宝山受控 4v4 测试场 | 独立匹配与结算，记录盟会活动贡献；不等于百人 GVG |

首次灰盒只加载必要场景；采用分区与明确过渡，不要求连续大世界无缝穿越。
场景切换期间显示加载状态，暂停发送移动输入；收到入区快照并完成资源加载后才恢复操作。
地标、出口和战斗活动范围必须可从第三人称镜头识别；碰撞体与视觉边缘保持一致。
进入场景前检查资源完整性与可用空间；加载失败可重试或返回，不能出现空场景和可操作的无碰撞角色。

## 4. 手机触控与精美画面

三职业均为普攻、2 个职业技能、闪避和宝宝指令；动作区按拇指触达范围排布，避免用缩小的 PC 技能栏。
左摇杆持续占用自己的 pointerId，右侧技能与镜头分别处理触点；同时移动、转镜头和施法时互不抢焦点。
技能按钮可拖动瞄准并划出取消；交互和救援使用情境按钮，危险预警不被手指、队伍栏或弹窗遮住。
触控热区按实际毫米和设备密度校验，建议最小约 9 mm；适配长屏、刘海、挖孔、圆角和系统手势安全区。
失去焦点、收到触摸取消或切后台时清空移动/蓄力输入；返回时不得补发积压触摸或误触购买、施法。
URP 使用移动质量档、烘焙环境光与受限动态主光，优先保障角色材质、轮廓、脚部接地和地面危险提示。
V0 制作约 60 米高品质路径，验证水面、植被、建筑、角色和宝宝在跑动、背光及四人技能叠加中的效果。
用 LOD、纹理分级、GPU Instancing、遮挡与粒子上限控制成本；远景阴影、反射、透明过绘优先降级。
Android 选定 Vulkan/OpenGL ES 兼容策略，iOS 使用 Metal；压缩贴图与着色器变体在目标设备验证，不按桌面结果推断。

## 5. 配置与状态归属

`ScriptableObject` 保存技能、宠物、敌人、物品、任务和场景的静态定义及表现资源引用。
配置使用稳定 ID，禁止把存档、当前生命、掉落结果或队伍成员写回共享配置资产。
可影响战斗结果的数值从同一份版本化数据源生成 Java 与 Unity 配置；不要维护两份手填平衡表。
服务器保存角色成长、库存、装备、宠物归属、任务进度及战斗权威状态；客户端只保留镜像与预测状态。
三职业无坚不摧/金刚护体/行动敏捷分别使用长刃/盾刃/双刃；可共用标准骨架，动作、判定和技能必须独立配置与验收。
世界解锁配置覆盖探险、海盗、机战、三国、龙珠；六宝山为智、文、珍、藏、龙、海盗，分别定义入口条件和活动规则。
原版参考门槛 25 级领养宝宝、35 级装备加品、42 级打造、65 级附魔由服务器校验；其他世界等级按主设计配置，不自行补造。
独立的 65 级系统测试存档使用单独的测试环境/数据命名空间，不能进入正式市场、排行榜或正式区活动；测试权限由服务器校验。
P2 实际实现打造、加品、附魔预览及服务端结算，不以只显示成长入口代替；概率、材料、降级/保护结果与装备版本必须一致记录。
原版魔 10 的 300% 基数与敏捷影响附攻附防的公式尚未明确；统一配置前不得按猜测填写为“旧版算法”。
首片只制作小镇、探险片区与文宝山；后续世界配置与完整可玩场景分开标记，不能用菜单入口表示内容已完成。
宝宝手感测试可使用明确标记的测试账号或演示伙伴，不把测试便利用作绕过正式 25 级领养门槛的玩家规则。
原型离线模式通过本地会话适配器产生同形状态，界面和技能表现仍走同一组事件；联网时替换适配器。
账号、角色、实体、房间和静态配置 ID 分开命名；C# 长整型使用 `Int64`，JSON ID 优先用字符串。
跨语言样本必须包含大于 `2^53 - 1` 的 ID，防止经过 JavaScript 或通用 JSON 工具时丢失精度。

## 7. 客户端连接与契约验证

连接路径：`Unity -> HTTPS 登录/短票据 -> WSS External -> Broker -> 实时区域/业务 Logic -> 数据存储`。
Bolt 是服务间通信；Unity 不直接连接 Broker，也不把 WebSocket 连接理解成可以随意发送 JSON。
实施第一项联网实验是核对 ioGame 21.25 实际 External 外部消息帧、消息体编码、路由号、错误码和心跳。
从项目协议导出流程获得权威字段定义，再生成或验证 C# 契约；核对 protobuf 字段号、缺省值、集合和 Int64。
保存 Java 编码/C# 解码与 C# 编码/Java 解码样本，覆盖认证、请求回应、服务器推送、未知字段和错误响应。
HTTP 登录成功后维护明确的会话容器，通过新增接口申请短效、一次性、绑定角色和目标服务的连接票据。
External 认证处理器校验票据、绑定 userId、消费 nonce；Cookie 登录本身不会自动认证游戏连接。
票据不放进 URL 或日志；重复使用、过期、登出、换角色和被踢下线都必须得到确定的失败结果。
原生会话不依赖浏览器自动携带 Cookie；需要持久保存的认证凭证使用平台安全存储，禁止明文 PlayerPrefs 保存密码。
UI 区分连接中、重连中、会话过期、服务不可用和版本不兼容；禁止悄悄跳过错误继续游戏。

## 8. 实时模拟与同步

建议从服务器固定 `20 Hz` 模拟起步，即每 tick 50 ms；这是待压测的设计起点，不是现有测值。
客户端按渲染帧采样输入，按约定频率提交输入序号、方向、朝向和动作意图；服务器决定有效位移和命中。
本地角色进行移动预测，依据服务器确认的输入序号校正并重放未确认输入；远端实体使用快照插值。
插值缓冲初值建议 100 ms，按抖动调节；客户端时间通过服务器时钟偏移估计，禁止直接信任客户端时间戳。
服务端快照包含 tick、区域版本、实体 ID、状态版本、位置、朝向和动作；加入/离开 AOI 有显式生命周期事件。
伤害、冷却、控制、宠物技能、死亡和掉落以服务器为准；客户端可提前播动作，不能提前永久结算收益。
原型限制高速位移和空中战斗，先做地面运动、胶囊碰撞与简单高度；技能判定用明确形状和服务器时间窗口。
Java 服务端采用经验证的导航/碰撞库并导出版本一致的行走与障碍数据；可评估 Recast4j，不能依赖 Unity NavMesh 在 Java 中运行。
Unity AI Navigation 负责本地演示与路径表现；服务端路径和碰撞决定结果，二者需要相同坐标、单位和关卡版本。
WSS/TCP 可能产生队头阻塞；先在目标延迟下测实际手感，是否另设实时传输服务必须由测量结果决定。
P1 必须以 4 台真实手机进行文宝山合作验收；编辑器、单人或机器人不能替代真实四人合作测试。
共享区域先从 8 人测到逻辑上限 16 人；按手机性能限制远处非相关玩家的完整模型与特效，队友和直接威胁不能隐藏。
AOI 决定服务器发送范围，表现预算决定模型/动画细节；降低表现不得导致不可见攻击、丢失目标或错过队伍救援。
文宝山迷宫机关、首领技能、倒地救援和结算按主设计配置；同一尝试锁定配置版本，断线不触发有利的即时难度重算。
P3 珍宝山只验收受控 4v4；服务器验证命中、阵营、冷却、贡献和结果，同步记录不同网络质量下的公平性。
每区 16 人和 4v4 都是待验收的原型规模，不构成百人盟会战、全服容量或正式 MMO 承载结论。

## 9. 移动生命周期、持久化与恢复

区域模拟每 tick 在内存运行，不按每个位置快照写 MongoDB；在检查点与可靠业务事件上保存必要状态。
奖励结算使用 `runId + encounterId + playerId + rewardType` 等稳定幂等键与唯一约束，重试返回同一份结果。
库存写入与结算记录必须具备事务或可恢复的一致性流程；先验证 MongoDB 部署是否支持所需事务。
跨区使用 transferId：源区冻结输入，目标区预留并确认接管，再提交角色归属；失败回原区或安全点。
归属版本号防止新旧区域同时接受输入；重复入场、回包乱序和切换时断线均要覆盖。
切后台立即停止新输入，服务器继续运行；来电、锁屏、系统冻结与杀进程均不保证客户端能发送退出消息。
前台恢复重新校验连接和票据，拉取完整快照、已结算奖励与队伍状态；Wi-Fi/蜂窝切换重建连接，避免并存两条有效输入流。
文宝山按主设计在断线 5 秒后离场，席位保留至断线起 60 秒；重连不能重置无敌、补发药品或重复贡献。
珍宝山 PvP 的后台和掉线由服务器继续按对局规则裁定，不通过主动断网获得不可攻击收益；重连保留原对局结果。
全员失去战斗能力后的重试、补给和救援遵循主设计；恢复数据必须包含本次尝试 ID，防止重连误建新尝试。
席位超时回安全点；进程重启时可放弃未完成战斗，但已确认奖励必须可恢复，任何恢复流程都不能复制奖励。
轻量真实交易只做固定价材料挂单/购买/撤单；服务器托管物品，扣款与交付幂等，禁止先扣客户端背包再异步补账。
交易验收覆盖同一挂单双买、余额不足、背包满、撤单与购买竞争、回包丢失重试；事务或可恢复流程必须保证守恒。
盟会成员、角色权限与基础积分持久化；积分以活动结算 ID 去重累加，离会/换会时历史归属不被重复转移。
记录输入拒绝、状态校正、模拟耗时、结算重试、跨区失败及重连成功率，用于判断系统是否可扩展。

## 10. 手机性能预算与验收环境

| 设备档 | 拟议目标 | 验收方式 |
| --- | --- | --- |
| Android 中档：骁龙 778G 级、6 GB RAM | 30 FPS，P95 帧时间不高于 40 ms | 安装 ARM64 APK，在战斗、城镇与长时运行中采样 |
| Android 高档：骁龙 8 Gen 2 级、8 GB RAM | 可选 60 FPS，P95 帧时间不高于 20 ms | 允许用户选择 30/60 档；验证升温后的持续性能 |
| iOS：iPhone 13 | 独立验证 30 FPS 基线，高档 60 FPS 需另测 | 使用 Mac/Xcode 与有效签名构建，在真实设备测性能和恢复 |

Android 初始内存预算不高于 1.5 GB，以进程 PSS 等明确口径测量并与 Unity 指标区分；记录加载峰值、后台回收与长期增长。
iOS 初始峰值内存预算 1.2 GB，记录系统测量口径、场景峰值与内存警告；两端均需根据实测调整，不能只看 Unity 托管堆。
首包加首区必要资源的总下载目标不高于 400 MB；分别记录 APK、下载缓存、解压后安装空间，避免混淆压缩包与磁盘占用。
分辨率与渲染比例按质量档记录，不固定以桌面 1080p 代替手机实际负载；温度、帧率、内存、画面质量一起验收。
每台目标手机连续 30 分钟运行，记录起始/稳定温度、帧时间分布、降频、电量消耗及内存；禁止只测冷机五分钟。
压力场景含 4 名玩家、4 只宝宝和多类活动敌人；共享区记录逻辑 16 人、实际表现数、AI 与特效数，珍宝山另测 8 人对抗。
Unity Profiler/Frame Debugger 配合 Android/iOS 平台工具定位 CPU、GPU、GC 和过绘；最终性能以真机安装包为准。
服务端参考环境：4 vCPU、8 GB RAM、同区域独立数据库；单房间 tick 执行 P95 目标小于 25 ms，并单测多房间。
联网验收配置记录 RTT 100 ms、抖动 30 ms、1% 网络丢包及 10 秒中断；WSS 丢包通过重传影响延迟，不当作消息丢失模型。
四台手机共斗时验收来电、锁屏、后台 10/60 秒、杀进程、Wi-Fi/蜂窝切换、网络恢复与版本过期，无复制奖励或永久卡死。
触控验收包含摇杆+镜头+技能同时操作、跨按钮拖动、系统边缘手势、输入法弹出、触摸取消和横屏两方向安全区。
Android 上的通过结果不能替代 iPhone 13；iOS 包必须额外验证签名安装、Metal 材质、内存压力与系统恢复行为。
所有上述硬件、人数和门槛均为建议验收基线，实施阶段登记测试结果与可接受调整原因。

## 11. 阶段门槛

团队规模、预算与可用资产尚未确认，阶段按验收推进，不承诺固定工作日或交付周数。
实施需要覆盖 Unity 手机客户端、Java 实时服务、技术美术/关卡、Android/iOS 构建和真机测试职责；职责确定后再排期。

| 阶段 | 必须交付 | 技术及体验门槛 |
| --- | --- | --- |
| P0：真机 5 分钟手感 | 可安装 APK，角色、触控、相机、三类基础敌人与宝宝指令；三职业逐一验证 | 新玩家能移动、转镜头、施法、躲预警；多指操作和焦点切换可靠 |
| V0：真机精美样板，与 P0 并行 | 约 60 米高品质路径、精制角色与宝宝、实际灯光和移动质量档 | 多机位和跑动中达到美术目标；中档手机热稳定后符合预算 |
| P1：四台手机共斗 | 三职业、砾灵/灯灵、文宝山迷宫试炼、山门守卫、权威模拟与个人结算 | 四台真实手机完成协作，技能和奖励一致；掉线、团灭及系统中断可恢复 |
| P2：养成与盟会闭环 | 15 至 20 分钟新手试炼、独立 65 级测试角色、打造/加品/附魔、宠物、基础盟会积分与持久化 | 新手与系统演示分别通过，扣料/结果/积分准确；8 人逐步测到逻辑 16 人共享区，性能降级不隐藏队友或威胁 |
| P3：受控对抗与市场 | 珍宝山 4v4、盟会活动记录、材料上架/购买/撤单与到账记录 | 八台手机验证阵营与贡献结算；并发交易和重试保持资产守恒，不声称百人 GVG |

P0 期间并行验证 External 契约与可信认证；P1 不通过时先解决同步和协作，再扩大场景。
P0 通过不代表 MMO 完成，V0 通过不代表五大世界或六宝山全部建成；按真机样板质量逐段替换灰盒。
按主设计招募 8-12 名外部测试者，至少两组四人；记录机制学习、宠物决策、合作与主动重玩，不能宣称已证明留存或商业可行性。

## 12. 首轮资源清单与削减顺序

最小资源：1 套玩家标准骨架，长刃/盾刃/双刃三职业分别验收普攻、2 技能与闪避；砾灵/灯灵各 1 主动，3 类普通敌人与山门守卫。
NPC 覆盖任务、宝宝领养、装备、盟会和交易功能；可复用骨架，通过服饰与道具区分职责。
关卡资源：镇/野外/副本各 1 个灰盒，加 1 段精美样板；统一建筑/地形模块，清晰出口、交互点与导航数据。
样板包含完整角色材质、近中远景构图、主辅光、植被、环境声、技能与预警；灰盒通过后按样板逐段替换。
表现资源：动作衔接、受击、闪避、三职业技能、宝宝协作与 Boss 预警；脚步、攻击、环境及结算音效。
界面资源：手机 HUD、队伍、任务、盟会、背包、宝宝、结算、下载/重连与设置；中文字体、图标与热区在真机逐页校验。
先削减：首片以外世界的完整制作、百人 GVG、复杂拍卖、住房、坐骑、额外宝宝外观；再减少支线、地图面积和重复装饰。
范围调整保留三职业差异、三类敌人、两宝宝、四人手机协作、基础盟会、精美样板质量以及 P3 受控 4v4 与材料市场。
若核心循环仍缺少重玩动力，优先调整 Boss 机制、宠物职责与奖励选择，再判断是否值得进入完整 MMO 制作。
